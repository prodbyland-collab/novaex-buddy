The member tools update adds recovery and verification emails, account timing and activity, retry controls, administrator audit history, complete payment histories, and an in-app notification inbox. The activity ticker and withdrawal completion behavior are unchanged.

Deploy in this order:

1. In Lovable Cloud's SQL editor, apply any pending earlier migrations first, particularly secure accounting (`20261004120000_secure_accounting.sql`) and ten-minute codes (`20261004140000_ten_minute_group_codes.sql`). The legal acceptance migration (`20261003200000_require_registration_legal_acceptance.sql`) and group announcements migration (`20261004080000_site_group_announcements.sql`) are prerequisites for secure accounting.
2. Run `supabase/migrations/20261004160000_member_tools.sql`. It creates audit and notification tables, verified-session access policies, notification triggers, and service-only audited administrator actions. It can be rerun safely. Audit history starts at deployment; old administrator changes cannot be reconstructed. Notifications are created for new events, not historical payments.
3. In authentication settings, ensure the published site URL is `https://teamgng.lovable.app` and the allowed redirect URLs include `https://teamgng.lovable.app/auth` and `https://teamgng.lovable.app/auth?mode=recovery`. Add the corresponding preview origins if testing recovery in preview. Enable/configure password recovery and signup verification emails using Cloud's auth mail service. The UI enforces a 60-second resend cooldown; the auth service enforces its own limits.
4. Let GitHub sync finish, then publish the update in Lovable. Audited administrator writes require the migration. They fail without it rather than making an unrecorded change.
5. With test accounts, verify a reset email returns to the new-password screen, an MFA account must verify its authenticator before changing its password, and old/expired recovery links prompt for a new link. Verify resend verification on an unconfirmed test account. Confirm a test plan/deposit event appears only in its owner's notification inbox, daily codes expire at 20:10 Georgian time, and administrator changes appear in Audit log.

The dashboard displays the existing daily payout cron schedule: 23:55 UTC, or 03:55 in Georgia. This is the scheduled processing time; actual payment depends on account eligibility and successful processing. Code publication remains 16:00 UTC (20:00 Georgia), active for ten minutes. Inbox polling runs every 30 seconds, account activity every minute, and chat refreshes every 15 seconds.

All database mutations are restricted to the existing verified authentication boundary. Financial audit entries commit in the same database transaction as their changes. Auth-provider operations record a durable pending intent first, followed by completed/failed. If a worker stops mid-operation, pending entries remain visible for investigation. Audit records retain account IDs and labels after deletion. Payment history is fetched completely and displayed in pages; very large accounts may need database pagination in a later scalability update.
